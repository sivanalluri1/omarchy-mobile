# SM-P613 input and mobile profile bring-up

The downstream kernel exposes sec_touchscreen and sec_e-pen, but the RAM init has no udev daemon. The desktop initially discovered neither input device. `native/setup-p613-input.py` creates RAM-only udev database classifications by kernel device name and grants the desktop's input group access to the corresponding event nodes. Power/volume keys are classified too. The script is guarded by the experiment marker, kernel revision and expected pen axis ranges.

Libinput accepted touch immediately, but rejected the pen for missing resolution. Live pen X/Y ranges were 0–13536 and 0–22560, with zero resolution; pressure was 0–4095. The pinned Samsung panel source (`drivers/gpu/drm/msm/samsung_lego/HX83102_TV104WUM/dsi_panel_HX83102_TV104WUM_wuxga_video.dtsi`, lines 65–66) specifies 135.3 × 225.6 mm. Supplying 100 units/mm with EVIOCSABS makes libinput accept the pen. This changes volatile kernel axis metadata only: ranges, current values, fuzz, flat, pressure and persistent calibration remain intact. The change disappears at reboot.

Hyprland then enumerated touch, tablet and two key devices. A bounded 120-second, non-grabbing libinput capture recorded 44 touch downs/ups, 325 touch motions, 26 pen proximity events, 52 tip transitions, 2,492 pen motion events and pressure from 0 to 0.9687. The owner confirmed that finger and S Pen both respond. Edge accuracy, orientation changes, palm rejection and button behavior have not been validated.

The real mobile home and launcher rendered in a RAM overlay; screenshots show the clock, Foot shortcut and bottom app search. The profile also enables the app switcher and back gesture. All plugin sources/helpers are from the pinned upstream archive. A narrow staged patch sends mobile desktop-entry launches through `p613-launch-desktop` (GIO) in the manual session, preserving upstream workspace/focus logic. It does not impersonate UWSM or start systemd. Subsequent clean testing verified Foot launching through the adapted path.

The interactive session did not pass stability validation: the IPC watchdog stopped Hyprland after a missed response. Processes then blocked in SquashFS page faults/decompression; available memory was around 200 MiB. This establishes the wait location, not the root cause. Native init/SSH remained usable. A clean native reboot and repeat are required before treating this mobile profile as stable. Earlier bar-only image and recovery artifacts are retained.

Build the observer with `buildenv/input.Dockerfile` and `scripts/build-input-probes.sh`. It reports aggregate event counts without publishing touch coordinates, does not grab input, and accepts an observation period of at most 120 seconds. `P613_ENABLE_INPUT=1` enables the classified input setup in images containing the helper. Libinput's required capabilities and metadata behavior are documented in its [tablet debugging guide](https://wayland.freedesktop.org/libinput/doc/latest/tablet-debugging.html) and [device quirks guide](https://wayland.freedesktop.org/libinput/doc/latest/device-quirks.html).


## Recents and allocation fixes

A fresh revision-4 image passed the complete 120-second home/launcher check and opened Foot through the adapted GIO path. The subsequent physical repeat identified a separate failure when an app was cleared from recents: the compositor rejected capture of a disappeared toplevel, and Quickshell lost its Wayland connection with an invalid-object error. The pinned Hyprland capture handler returns before creating a requested frame when the window is absent. The P613 staged profile now uses static labeled app cards; live captures remain an explicit opt-in pending a protocol fix. Switching and closing remain available.

Repeated app lifecycles also exposed a Turnip allocation descriptor leak. The ION/DMA-heap allocation helpers passed a newly allocated fd to an import routine that duplicates it, but never closed the original. A hardware Vulkan regression proved a delta of +64 descriptors across 64 allocation/free cycles in the original library and zero in the repaired library. GPU pixel readback still matched. The patch changes ownership in the three allocation helpers, preserving the original tested driver build in a separate output directory.

With repaired Turnip and static recents, ten real Foot open/close cycles passed while recents remained visible. Each cycle verified a new mapped window, actual close, responsive shell and loaded home. ION usage was around 330 MiB at the live check instead of growing to roughly 1.7 GiB in the failed workload. This is bounded evidence, not long-duration certification. The failed runs and their logs are retained. Driver evidence: build-records/mesa-fd-fix-build.json.

Reproduction uses `scripts/build-mesa-fd-fix.sh` before rebuilding the Omarchy image. `scripts/test-mobile-lifecycle.py --close-test-windows --cycles 10` refuses a different BOOT or non-Foot application windows; it closes the test terminals. The launcher accepts `P613_QSG_RENDER_LOOP=basic` for the single-context Qt run and `P613_EXPECT_MOBILE=1` for home/launcher state checks. Qt documents its render loops in [QQuickWindow](https://doc.qt.io/qt-6.12/qquickwindow.html). This setting alone did not fix the recents protocol failure or the allocation leak.


## Final immutable image

Revision 5 includes both the allocation fix and static recents patch. A clean mount without diagnostic overlays passed the complete 120-second session and ten more app lifecycle cycles. The final library also passed GPU pixel readback and the 64-allocation zero-descriptor-growth test. Five-second samples retained at least 1,548,816 KiB available; maximum sampled ION heap use was 520,108 KiB. Non-BOOT partitions still match their original backups, and BOOT matches the native test candidate. The owner authorizes leaving Linux active. The one-hour desktop session was started for continued testing and is not counted as a completed stability test. The user confirmed that clearing Foot from recents leaves the status bar and recents/home visible and responsive. See build-records/hardware-test-08.json.
